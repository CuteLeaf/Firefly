在 RAG 系统里，文档切分经常被简化成一个参数：`chunk_size=500`。这个参数很容易配置，却足以决定检索系统的大部分性格。

块太小，向量表达更聚焦，但答案所需的条件、例外和结论可能被切散；块太大，上下文更完整，但多个主题会挤进同一个向量，真正相关的信息反而难以被召回。Overlap 太少，边界处的信息容易丢失；Overlap 太多，索引膨胀、重复召回和重排浪费又会接踵而来。

更麻烦的是，所谓“最优 Chunk”并不是文档本身的固有属性。它同时取决于用户怎样提问、Embedding 模型如何表达、检索器怎样召回、重排器能处理多少候选、生成模型需要多少证据，以及系统是否要求精确引用。相同的一份制度文档，用于“某个报销上限是多少”和用于“总结完整报销流程”，理想切法并不相同。

因此，生产级文档切分不是把长文本裁成短文本，而是建立一种**可检索的知识边界**：既让检索器容易命中，又让生成模型拿到足够、可信、可定位的证据。

上一篇 [《RAG 文档解析工程》](/posts/rag-document-parsing-guide/) 讨论了如何把 PDF、Word、Excel 转换成结构化内容。本文从这个结果继续向下，集中回答四个问题：

1. 主流切分策略分别解决什么问题，又会制造什么新问题？
2. 不同文档、查询和业务目标应该如何选择策略？
3. 工业生产环境中，成本、权限、增量更新和可观测性如何影响切分设计？
4. 怎样通过真实评估判断切分有效，而不是凭感觉调整参数？

> 本文不会寻找一个“万能切分器”。我的结论恰好相反：可靠系统通常采用结构优先、内容类型感知、Token 受控的混合切分，并把检索单元与生成单元分开设计。

## 一、先定义目标：Chunk 到底为谁服务

一条典型 RAG 链路可以简化为：

```text
原始文档
→ 解析与结构重建
→ 语义单元
→ Chunk
→ Embedding 与索引
→ 召回
→ 重排与上下文组装
→ 生成答案与引用
```

切分处在中间，却同时受上下游约束。

### 1.1 Chunk 不是越“语义完整”越好

从阅读体验看，一整章当然比一个段落完整；从检索角度看，一整章可能同时包含定义、流程、例外、案例和附录。将它压缩成一个向量，相当于要求一个坐标代表多个方向，结果往往是每个主题都表达得不够突出。

反过来，一个句子虽然主题纯净，却可能只写着“上述情形除外”。它在语法上完整，在业务上毫无独立意义。

所以 Chunk 至少要同时满足四个目标：

- **可发现：** 用户的表达能够与块中的核心语义建立匹配；
- **可回答：** 块内包含回答问题所需的主体、条件、结论和必要限定；
- **可组合：** 多个块被召回后不会产生大量重复、冲突或顺序混乱；
- **可追溯：** 每个结论能定位回原文的章节、页码、表格或其他来源位置。

这四个目标彼此冲突。切分工程的本质不是找到最大值，而是根据业务选择损失更小的平衡点。

### 1.2 区分四种容易混淆的“单元”

生产设计中，我建议明确区分：

| 单元 | 作用 | 典型大小 |
| --- | --- | --- |
| 原子语义单元 | 不宜继续拆开的段落、条款、列表项、表格行、代码函数等 | 由文档结构决定 |
| 索引单元 | 用于 Embedding、关键词索引和初始召回 | 通常较小、主题集中 |
| 重排单元 | 送给 Reranker 判断相关性的内容 | 可等于索引单元，也可附带邻近上下文 |
| 生成单元 | 最终交给大模型作为证据的内容 | 通常比索引单元更大、更完整 |

很多系统只有一种 Chunk，然后让它同时承担四项职责。这种设计简单，却会把检索精度和答案完整度绑死。更灵活的做法是“小块召回、大块回答”：用聚焦的子块找到位置，再展开父章节、相邻窗口或完整表格给生成模型。

## 二、决定切分方案的六个变量

在讨论算法前，先看真正影响选型的变量。

### 2.1 查询粒度

- **事实查询：** “试用期是多少个月？”通常适合较小、主题单一的块；
- **条件查询：** “哪些情况下可以免审批？”需要条件和例外处在一起；
- **流程查询：** “采购申请到付款要经过哪些环节？”需要多个步骤或更大的父块；
- **比较查询：** “A 方案和 B 方案有什么差异？”可能需要跨章节组合；
- **总结查询：** “概括整份报告的风险”不能依赖单个局部块。

如果业务查询类型差异很大，试图用一个 Chunk 尺寸覆盖全部场景通常不会成功。

### 2.2 文档结构质量

HTML、Markdown、规范 DOCX 往往有可靠标题树；扫描 PDF 可能只有坐标和 OCR 文本；客服对话、邮件线程和日志则有时间、说话人等另一种结构。结构越可靠，越应该优先使用结构边界。结构缺失时，才需要句子、语义相似度或模型推断补位。

### 2.3 内容类型

自然语言段落可以按句子组合，表格必须携带表头，代码要尊重语法节点，合同要保留条款层级，对话要保留说话人和轮次。把所有内容先转成纯文本，再交给同一个分隔器，是许多质量问题的源头。

### 2.4 模型与检索器约束

- Embedding 模型有最大 Token 长度，超长内容可能被截断；
- 不同 tokenizer 对中文、英文、代码和数字的计数差异明显；
- 稠密向量、BM25、稀疏向量对长块的敏感方式不同；
- Reranker 的最大长度和调用成本限制候选规模；
- 生成模型上下文再长，也不代表应该塞入大量重复证据。

切分参数必须围绕实际部署模型计算，不能只使用字符数，更不能照抄另一个项目的经验值。

### 2.5 更新与版本特征

政策文档按版本整份替换，产品手册可能只修改一节，Wiki 页面持续小步编辑，工单和对话则不断追加。切分越依赖全局语义或模型生成，局部修改后受影响的块可能越多，增量重建成本也越高。

### 2.6 风险与引用要求

普通内部搜索允许返回一个相关章节；医疗、法务、金融等场景则要求条件、例外、版本和出处精确一致。高风险业务宁可保留更明确的层级与来源，也不应为了向量“纯净”把限定条件拆掉。

## 三、基础切分策略：简单不等于没有价值

### 3.1 固定字符数切分

按照固定字符数截取文本，是最直接的策略。

**适用场景：** 快速原型、结构极差的纯文本、对切分质量要求较低的日志或临时语料。

**优点：** 实现简单、吞吐稳定、资源容易估算，结果也相对确定。

**问题：** 中文、英文、数字和代码的字符与 Token 比例不同；固定位置会切断句子、编号和表格；看似同样长度的块，进入模型后的实际成本可能差异很大。

我的判断是：固定字符切分可以作为基线和故障回退，但不应成为知识库的默认生产方案。它最大的价值不是效果好，而是提供一个足够稳定的对照组，帮助判断复杂策略是否真的带来收益。

### 3.2 固定 Token 数切分

用目标模型的 tokenizer 按 Token 控制大小，解决了模型长度预算不准确的问题。

**适用场景：** 大规模无结构语料、模型输入限制严格、成本需要精确控制的系统。

**优点：** 块大小与 Embedding、Reranker 和生成模型的真实限制一致，容量规划更可靠。

**问题：** Token 边界仍然不是语义边界；更换模型后需要重新审视参数；不同阶段如果使用不同 tokenizer，还需要为各阶段保留安全余量。

Token 控制应该是所有策略的“护栏”，而不是完整策略本身。更合理的做法是先按结构和语义确定候选边界，再用 Token 上限处理超长单元。

### 3.3 滑动窗口与固定 Overlap

每个块与前后块重复一部分内容，可以降低答案恰好跨边界时的丢失风险。

**适用场景：** 连续叙述文本、转录稿、结构不可靠的普通段落，以及只能使用固定长度切分的系统。

**优点：** 简单有效，对边界错误有一定容错能力。

**生产代价：**

- 索引体积和 Embedding 成本按重叠比例增长；
- 多个近重复块同时进入 Top-K，挤掉其他证据；
- Reranker 和生成模型重复处理同一句话；
- 引用结果可能出现多个几乎相同的位置；
- 删除或更新内容时，受影响块的范围扩大。

Overlap 是一种补偿机制，不是一种语义理解。生产中应只对“被迫拆开的连续正文”增加重叠，并尽量对齐完整句子；标题路径、表头和父级上下文应该结构化补充，而不是靠复制正文解决。

## 四、基于文本边界的策略

### 4.1 分隔符与递归切分

递归切分通常按“章节 → 段落 → 句子 → 词或字符”的顺序寻找可用边界：当前层级超长时，才进入更细一级。

**适用场景：** Markdown、普通网页、层级较清晰的纯文本，以及需要一个通用默认策略的场景。

**优点：** 比固定长度更尊重自然边界，计算便宜、结果确定、容易调试。

**问题：** 分隔符只代表排版，不一定代表语义。PDF 中每行换行并不是段落；用户在 Markdown 中可能滥用标题；中文标点、英文缩写、小数点和编号会让句子识别出错；表格和代码中的换行更不能按正文规则处理。

递归切分适合作为混合方案的最后一层，而不应该在丢失文档结构后独自承担全部判断。

### 4.2 句子切分与句子窗口

先识别完整句子，再将若干相邻句组成索引块；召回后展开前后句子窗口。

**适用场景：** 新闻、论文正文、访谈、说明性文章等句间关系连续的内容，尤其适合细粒度事实检索。

**优势：** 索引单元主题集中，生成阶段仍能获得局部上下文；窗口大小可以在查询时调整，不必把所有重复内容写进索引。

**风险：** “本办法自发布之日起施行”这样的句子离开标题和前文无法独立理解；窗口可能跨越小节边界，带入无关内容；OCR 错误标点会破坏句子识别。

因此，句子窗口必须受章节、列表、表格和权限边界约束。窗口是局部展开，不是无条件取前后 N 句。

### 4.3 段落切分

段落是最接近作者表达意图的基础单位之一，适合短文档、Wiki 和结构良好的业务说明。

但段落长度差异很大：有的只有一个标题式短句，有的包含数千 Token。生产中通常要把短段落与同主题邻居合并，对超长段落按句子继续拆分。不能简单地规定“一段等于一个 Chunk”。

## 五、结构感知切分：大多数企业知识库的主干

结构感知切分先恢复文档层次和内容类型，再沿真实业务边界切分。

### 5.1 标题层级切分

以文档的标题树作为主要边界，每个块携带完整 `heading_path`，例如“员工手册 → 休假管理 → 病假 → 证明材料”。

**适用场景：** 产品手册、规章制度、技术文档、Wiki、论文和报告。

**优点：** 符合作者组织知识的方式，引用清晰，父子关系天然可用。

**问题：** 一个章节可能过长，仍需二次切分；标题本身可能依赖上级语境；解析器恢复的标题层级未必可靠；某些文档只有视觉标题而没有结构标签。

实践中，标题路径应该作为检索上下文与元数据保留，但不宜在每个块中机械重复过长的完整目录。可以将精简标题写入检索文本，将完整路径放入元数据和展示层。

### 5.2 条款、列表与步骤切分

合同、制度和操作手册往往以“条—款—项”或步骤序列表达逻辑。切分时应保留上级条款、前置条件、警告和例外。

**适用场景：** 法务合同、合规制度、SOP、操作指南、故障处理手册。

一个常见错误是把每个列表项单独索引。列表项可能只有“由部门负责人审批”，问题中的审批对象却在列表引导句里。更稳妥的做法是把引导句、相关列表项和必要的父级标题组成一个最小可回答单元；超长列表再按语义组拆分，并为每组重复必要的引导信息。

### 5.3 表格感知切分

表格不能被当成用换行和竖线拼起来的普通文本。切分时至少要保留表名、列名、多级表头、单位、主键、脚注和数据行之间的关系。

**常用方案：**

- 小表整体作为一个块；
- 大表按行或业务实体分组，每组携带表头；
- 纵向连续记录按时间窗口或主键范围切分；
- 宽表按业务相关列族拆分，但共享主键；
- 汇总行、脚注和单位与对应数据绑定；
- 同时建立表级摘要索引与行级精确索引。

**适用场景：** 财务报表、产品参数、价格表、指标清单、Excel 业务数据。

工业环境中的关键权衡是：行级块适合查精确记录，却不适合回答趋势和汇总问题；整表块保留全局关系，却常常超过模型限制并稀释向量。表级摘要用于发现表，行级或行组块用于取数，是比“选择一个大小”更实用的双层设计。

### 5.4 代码感知切分

代码应按模块、类、函数、方法、配置段或语法树节点切分，并携带文件路径、符号名、依赖关系和必要的 import/类型上下文。

**适用场景：** 代码问答、仓库搜索、故障定位、API 使用说明。

只按行数截断会切开函数或把注释与实现分离；但把整个大文件作为一块，又会混合大量不相关符号。较好的方案是用符号级索引召回，再展开所属类、调用者或相邻定义。生成阶段是否需要依赖代码，应由查询和重排结果决定，而不是永久复制进每个块。

### 5.5 对话、邮件与时间序列切分

客服会话、会议记录和邮件线程的结构不是章节，而是轮次、参与者、时间和主题变化。

**常用边界：**

- 完整问答对或相邻多轮；
- 主题切换点；
- 明确的时间间隔；
- 工单状态变化；
- 邮件引用层级与新回复部分。

不能只按时间窗口切分，因为一次问题解决可能跨越很久；也不能只按说话人切分，因为单句话通常缺少上下文。对话中还要区分“当时的猜测”和“最终解决方案”，否则 RAG 可能召回已经被后续推翻的中间结论。

### 5.6 页面与版面区域切分

按页切分实现简单，也便于引用，但页面是排版单位，不是语义单位：一个段落可能跨页，一页也可能包含多个主题。

**适用场景：** 强调页码证据的 PDF、幻灯片、票据和视觉布局重要的文档。

更合理的做法是让页码成为来源范围，而不是绝对边界。跨页段落和跨页表格可以合并，同时记录多个页面；幻灯片则往往可以“一页一主题”，但演讲者备注和图表说明仍需一起处理。

## 六、语义驱动的切分策略

### 6.1 基于 Embedding 相似度的语义切分

语义切分通常先把文本拆成句子，计算相邻句或句组的向量相似度，在语义变化明显的位置建立边界。

**适用场景：** 缺少可靠标题的长篇叙述、转录稿、主题自然迁移的文章和报告。

**优点：** 能发现排版没有标出的主题变化，比固定窗口更贴近内容。

**生产问题：**

- 阈值高度依赖文档领域和 Embedding 模型；
- 相邻句始终相似的长章节可能形成超大块；
- 短句、代词和过渡句的向量不稳定；
- 每个句子都要计算向量，处理成本显著增加；
- 模型升级后边界变化，导致大量 Chunk ID 和索引失效；
- 语义突变不一定适合切开，例如“但是，以下情况除外”恰恰必须与前文绑定。

我的建议是：语义相似度适合在“同一结构节点内部”辅助寻找边界，不适合覆盖标题、条款、表格等可靠结构，更不应该独自决定高风险文档的边界。

### 6.2 聚类式主题切分

聚类方法根据句子或段落的向量，将相似内容归到同一主题。它适合分析主题分布、构建专题页或离线整理知识。

但对于普通 RAG 切分，聚类可能打乱原文顺序，把相隔很远但主题相似的段落拼在一起，破坏条件、时间和因果关系。因此它更适合作为索引的附加组织层，而不是替代原文连续 Chunk。

### 6.3 基于语言模型的主题边界判断

可以让语言模型识别主题切换、生成段落标签或决定哪些内容应该组成一个块。

**适用场景：** 结构极不规范但价值较高的文档、复杂会议记录、人工规则难覆盖的小规模专业语料。

**优势：** 能利用更丰富的语义和业务说明做判断。

**代价与风险：** 延迟和费用高，输出存在随机性，模型可能遗漏内容或重写原意，提示词与模型版本变化会影响边界，敏感数据还涉及外部处理合规。

生产中应限制模型只输出边界和标签，不允许它在切分阶段改写事实；保留原始跨度、模型版本和决策记录；对输出做覆盖率校验，保证所有原文都被且只被合理映射。

## 七、信息重写与多表示策略

这类方法严格说不只是“切分”，却经常与切分一起决定索引质量。

### 7.1 命题切分（Proposition Chunking）

命题切分把复杂段落拆成可独立理解的事实陈述，例如将一个包含多个主体和条件的段落拆成若干原子命题。

**适用场景：** 事实密集的百科、研究报告、产品知识和实体关系检索。

**优势：** 每个索引单元语义集中，适合精确事实召回和知识图谱结合。

**问题：** 生成命题需要模型成本；代词消解和上下文补全可能引入错误；条件、否定、时间范围与例外容易在原子化时丢失；一个段落会膨胀为很多索引项；引用仍然要回到原文，而不是引用模型生成的命题。

在医疗、法务等高风险场景，我不会让生成命题成为唯一证据。它可以作为“检索指针”，命中后必须返回对应原文块，由原文承担最终回答和引用。

### 7.2 摘要索引

为章节、表格或大块生成摘要，用摘要参与召回，命中后返回原文。

**适用场景：** 长章节发现、报告级搜索、跨段落主题查询、表格和图片等难以直接向量化的内容。

摘要可以减少长文本的主题稀释，但也会丢失细节，甚至引入模型没有依据的概括。生产系统应保存摘要到原文的一对一或一对多映射，摘要只用于路由，不作为事实证据。

### 7.3 问题生成索引

为每个块生成它可能回答的问题，将这些问题作为额外检索表示。

**适用场景：** FAQ、客服知识库、用户表达与文档措辞差异很大的业务。

它能缩短“用户问法”和“文档写法”的语义距离，但生成问题的覆盖率有限，也可能让检索偏向模型想象出的常见问题。应与原文、关键词和标题索引并存，并监控生成问题是否产生业务偏见。

### 7.4 上下文化切分（Contextual Chunking）

为每个局部块补充它在整篇文档中的简短上下文，例如文档主题、所属章节、指代对象和时间范围，再对增强后的文本建立索引。

**适用场景：** 大量短块离开文档后难以理解、标题信息不足、同名实体较多的知识库。

这能显著改善“本政策”“该产品”“上述限制”等孤立表达，但上下文生成会增加离线成本，也可能把不准确的解释传播到全部块。优先使用确定性的标题路径、实体字段和文档元数据；只有这些信息不足时，再使用模型生成上下文。展示和引用仍应使用原文，不能把补充文字伪装成原始内容。

## 八、层次化与多粒度策略

### 8.1 Parent-Child（父子块）

文档先切成较大的父块，再从父块中产生较小的子块。子块用于索引和召回，命中后返回父块。

**适用场景：** 制度、手册、论文、技术文档等既需要精确召回又需要完整上下文的内容。

**优点：** 直接化解“小块容易找、大块容易答”的冲突，是我最常推荐的生产方案之一。

**问题：** 多个子块可能指向同一父块，需要按父 ID 去重；父块过大仍会污染上下文；一个答案跨越两个父块时还需邻接展开；父子映射和版本更新增加存储复杂度。

父块不必机械固定为 1500 Token，它更应该是一个完整小节、条款组或表格；子块则可以是段落、条款项或句组。结构完整性优先，Token 上限负责兜底。

### 8.2 Small-to-Big 与邻接展开

先召回小块，再按需要向前后扩展相邻块、所属章节或关联对象。与 Parent-Child 相比，它的上下文范围可以在查询时动态决定。

**适用场景：** 查询粒度差异大、文档顺序关系强、希望控制上下文预算的系统。

关键是设置停止条件：不能因为一个块相关，就把整个文档都展开。可以综合重排分数、章节边界、Token 预算、内容类型和重复率决定扩展范围。

### 8.3 多粒度并行索引

同时建立文档级、章节级、段落级甚至命题级索引，查询时先判断意图或并行召回，再合并结果。

**适用场景：** 同时支持事实、流程、比较和总结问题的企业搜索平台。

**优势：** 不同查询可以命中合适粒度，避免一个尺寸承担全部任务。

**代价：** 索引量、Embedding 成本和检索编排复杂度明显增加；不同粒度的分数不能直接比较；去重和引用合并更困难。

只有当真实评估证明查询粒度确实多样，而且单层 Parent-Child 无法满足时，才值得增加多粒度索引。架构上的“更全面”不等于业务上的“更有效”。

### 8.4 层次聚合树

将底层块逐级聚合并生成更高层摘要，形成从局部事实到全局主题的树形结构。查询可以在不同层级检索，再下钻到原文。

**适用场景：** 超长报告、论文集合、跨文档总结和研究型问答。

它擅长全局问题，但树构建成本较高，摘要误差会向上累积；新增或修改底层内容后，需要重新计算受影响的祖先节点。对于普通 FAQ 和精确制度查询，这往往属于过度设计。

## 九、Late Chunking：先编码长上下文，再生成块表示

传统方案先切块，再分别计算 Embedding，因此每个块看不到文档其他部分。Late Chunking 的思路是先让长文本经过支持长上下文的编码器，再根据预定边界对 Token 表示做池化，得到每个块的向量。这样块向量可以包含更大范围的上下文信息。

**适用场景：** 代词、缩写和实体指代密集的长文档，以及局部段落必须依赖前文才能理解的语料。

**优势：** 不需要把大量上下文文本复制到每个块，也能让向量感知全局语境。

**生产约束：**

- 依赖特定模型和编码方式，不是所有 Embedding API 都支持；
- 文档长度仍受模型上限影响，超长文档要先分区；
- 整段编码对显存、吞吐和批处理提出更高要求；
- 文档局部修改可能导致较大范围的向量重算；
- 它改善的是块表示，不会自动修复错误的结构边界，也不会替代父块展开。

我更愿意把 Late Chunking 看作“Embedding 上下文策略”，而不是免除切分设计的捷径。原子语义单元、来源映射和生成上下文仍然必须存在。

## 十、动态与查询感知切分

静态切分在入库时完成，所有查询看到同一套块。动态切分则根据用户问题，在召回或生成前重新组合相关段落、表格和邻居。

**适用场景：** 查询类型差异大、文档结构化程度高、对答案质量要求高且允许更多在线计算的系统。

一种实用方式不是每次从原文重新切，而是预先保存细粒度语义单元和关系图，查询时动态组装：事实问题只取命中段落，流程问题扩展完整步骤，比较问题沿实体关系拉取多个章节。

**风险：** 在线延迟增加，缓存命中下降，行为更难复现；查询分类或模型决策错误会选错范围；动态组装还必须严格遵守 ACL，不能通过邻接扩展跨越权限边界。

查询感知方案适合作为静态可靠底座之上的增强，而不是第一版系统的起点。

## 十一、不同内容与业务场景的推荐策略

| 场景 | 首选策略 | 常见增强 | 主要风险 |
| --- | --- | --- | --- |
| 企业制度、员工手册 | 标题/条款结构 + Parent-Child | 子块召回、父块回答；保留例外和版本 | 条件被拆散、旧版本混入 |
| 产品与 API 文档 | 标题结构 + 段落/代码符号切分 | 关键词混合检索、邻接展开 | 版本、参数与示例错配 |
| 合同与法务文档 | 条—款—项层级切分 | 父级标题补全、多跳关联 | 否定、例外、定义域丢失 |
| 论文与研究报告 | 章节结构 + 语义辅助切分 | 摘要层、图表块、层次检索 | 引文与结论脱离、跨节推理 |
| FAQ 与客服知识 | 问答对整体切分 | 问题生成、多问法索引 | 相似问题互相污染 |
| 客服对话与会议记录 | 轮次 + 主题窗口 | 最终结论标记、时间过滤 | 中间猜测被当成结论 |
| Excel 与大型表格 | 表级摘要 + 行/实体组块 | 结构化查询、表头上下文 | 数值关系和单位丢失 |
| 新闻与普通文章 | 段落/句子组合 | 语义边界、句子窗口 | 指代不清、跨段条件遗漏 |
| 代码仓库 | AST/符号切分 | 调用关系、类级父块 | 依赖上下文缺失 |
| OCR 扫描文档 | 版面块 + 结构恢复 | 低置信度复核、局部 Overlap | 错字导致边界和召回双重失真 |
| 跨文档研究与总结 | 多粒度或层次聚合 | 文档级摘要、实体关联 | 摘要误差、成本过高 |

这张表不是模板答案。它真正想说明的是：切分策略应该由内容结构和查询任务共同决定，而不是按文件扩展名决定。一个 PDF 可能是合同、论文、幻灯片或扫描表格，它们需要完全不同的边界。

## 十二、生产环境最容易被忽略的问题

### 12.1 Chunk ID 必须稳定

如果每次重建都用数组下标生成 ID，那么文档开头增加一句话，后面全部块都会变成“新块”。这会造成向量全量重建、缓存失效、用户收藏和引用断裂。

稳定 ID 应综合文档稳定标识、结构路径、来源跨度、内容哈希和切分版本。局部内容变化时，只更新受影响块；结构发生大调整时，再明确生成新版本并维护旧引用映射。

### 12.2 切分规则必须版本化

需要记录解析器版本、切分策略名、参数、tokenizer、Embedding 模型和上下文增强版本。否则线上效果变化后，无法回答“某个块当时为什么这样切”。

新策略上线不应直接覆盖旧索引。更稳妥的方式是影子构建或双索引对比，用相同查询集比较后再迁移，并保留回滚能力。

### 12.3 权限不能在切分后补救

如果一个块合并了不同权限的内容，检索时无法安全地只展示其中一部分。ACL、租户、保密级别、有效期等边界必须参与语义单元构建和块合并。

Parent-Child 和邻接展开尤其容易越权：子块可见不代表整个父块可见；前后相邻内容也可能属于不同权限范围。扩展前必须重新验证目标块权限，而不是继承初始命中块的判断。

### 12.4 删除与时效性

生产知识库不仅会新增，还会撤回、过期和删除。系统必须能从文档版本找到全部派生的子块、摘要、生成问题和父节点，并彻底更新索引与缓存。

对于制度、价格和产品版本，块中应保留生效时间与失效时间。两个内容相似但时间不同的块不能仅靠向量相似度去重，否则可能删除有效的历史证据或召回过期规则。

### 12.5 去重不能只比较文本

Overlap、页眉页脚、模板段落和多版本文档会制造大量重复。近重复块会占满 Top-K，使检索结果看似相关却缺少多样性。

去重需要区分：

- 同一来源因 Overlap 产生的局部重复；
- 不同页面的模板性重复；
- 不同版本中合法保留的相同条款；
- 多份文件引用同一标准形成的跨文档重复。

可以在召回后按父块、来源跨度和文本指纹做多样化，但不能把“内容相似”直接等同于“可删除”。来源、版本和权限可能不同。

### 12.6 多语言与分词

中文没有天然空格，日文、泰文、德文复合词、阿拉伯文方向以及中英文混排都有各自边界问题。句子识别器、tokenizer 和 Embedding 模型必须覆盖真实语料。

同一个“500 字符”在不同语言中的 Token 成本不一致。多语言知识库更适合使用统一 Token 预算加语言感知的句子边界，并按语言分别评估，不要让英语测试集代表全部效果。

### 12.7 Embedding 截断必须显式检测

部分服务遇到超长输入会静默截断。此时索引记录看似包含完整 Chunk，向量实际只表达了开头部分，是非常隐蔽的线上问题。

入库前要用对应 tokenizer 计算长度，保留模型安全余量，并监控被强制二次切分和截断拒绝的比例。任何静默截断都应视为数据质量故障。

### 12.8 成本不是只有向量存储

更小的块和更多 Overlap 会同时增加：

- Embedding 调用量；
- 向量与关键词索引体积；
- ANN 检索和过滤开销；
- Reranker 候选数量；
- 上下文去重与组装成本；
- 更新、删除和备份耗时；
- 线上日志与可观测数据量。

一个策略即使 Recall 提升，也要检查单位有效答案成本。如果提升主要来自索引数量翻倍，可能通过混合检索、重排或父块展开以更低成本获得同样收益。

### 12.9 吞吐、缓存与重试

确定性结构切分适合缓存和局部重跑；语义切分、上下文生成和命题生成成本更高，应保存中间结果。缓存键至少包含原文哈希、策略配置、模型与提示词版本。

失败重试要区分临时错误和确定性错误。模型限流可以重试，某段永远超过上限则应进入规则回退；不要让一份异常文档在后台无限消耗资源。

### 12.10 可观测性不能只看平均 Chunk 长度

建议至少监控：

- Chunk 数量、Token 长度的 P50/P95/P99；
- 超短块、超长块、空块和孤立标题比例；
- Overlap 带来的索引膨胀率；
- 单文档近重复率；
- 结构边界降级到字符切分的比例；
- Embedding 截断或拒绝比例；
- 父块展开后的平均上下文增长；
- 各文档类型、语言和业务域的检索质量；
- 切分版本变化前后的回归差异。

平均值会掩盖尾部故障。真正导致投诉的，常常是少量超大表格、错误 OCR 页面或被拆散的关键条款。

## 十三、怎样评估切分，而不是凭感觉调参数

### 13.1 不要只做“看起来合理”的人工抽检

打开几个块观察边界是必要的，但不能代表检索效果。一个块读起来很完整，不代表用户问法能召回它；一个看似短小的块，也可能通过父块展开给出完美答案。

评估应分成三层。

### 13.2 第一层：切分内在质量

检查不依赖查询的基本质量：

- 完整性：原文是否有遗漏或非预期重复；
- 边界完整性：句子、条款、列表、表格和代码结构是否被破坏；
- 独立可理解性：主体、时间、条件和指代是否足够明确；
- 长度分布：是否存在大量异常短块或超限块；
- 来源映射：能否精确回到页码、章节和原始位置；
- 权限一致性：块内部是否跨越 ACL 边界。

### 13.3 第二层：检索质量

建立来自真实业务日志的查询集，并人工标注支持答案的最小证据范围。重点观察：

- Recall@K：正确证据是否出现在前 K 个结果；
- Precision@K：前 K 个结果中有多少真正有用；
- MRR 或首个正确结果排名；
- 父块展开后是否包含完整答案；
- 重复结果是否挤占候选；
- 关键词、稠密向量和混合检索下的差异。

只标注“相关文档”还不够。切分评估需要标注到段落、条款、表格行或来源跨度，否则无法判断失败发生在文档路由、召回还是块边界。

### 13.4 第三层：端到端答案质量

最终还要评估：

- 答案正确性与完整性；
- 条件、否定和例外是否保留；
- 引用是否真的支持对应结论；
- 上下文中无关和重复 Token 的比例；
- 延迟、Embedding/Reranker/生成成本；
- 无答案问题是否能够拒答，而不是拼凑相邻块。

切分优化最终应该服务端到端目标。有时较小块提升 Recall，却因为生成上下文碎片化而降低答案完整度；有时父块让答案更完整，却带来更多无关信息。只有联合评估才能看见这些交换关系。

### 13.5 测试集必须覆盖困难查询

至少包括：

- 答案恰好跨越候选边界的问题；
- 需要标题或上级条款才能理解的问题；
- 包含否定、例外、单位和时间范围的问题；
- 需要表头与数据行共同回答的问题；
- 多个版本内容相似但答案不同的问题；
- 需要多个块组合的流程、比较和总结问题；
- 文档没有答案的拒答问题；
- 多语言、缩写、别名和口语化问法。

如果测试集只有单句事实题，得到的最优策略几乎一定会偏向小块，并掩盖真实业务中的组合推理问题。

## 十四、我的生产选型：从朴素混合方案开始

如果要为一个典型企业知识库设计第一版，我会采用下面的顺序。

### 14.1 先建立可靠的语义单元

从解析层保留标题、段落、条款、列表、表格、图片说明、代码符号、页码和 ACL。不要过早把它们压成纯文本。结构证据不可靠时标记置信度，并允许降级。

### 14.2 结构优先组合，Token 上限兜底

优先沿标题、条款、段落和内容类型边界组合。短小且同主题的相邻单元可以合并；单个单元过长时，再在其内部使用句子或递归边界切分。Token 预算由实际 Embedding 和 Reranker 模型决定。

初始实验可以从以下范围出发，而不是把它当成标准答案：

- 事实型子块：约 200～400 Token；
- 通用知识子块：约 300～600 Token；
- 父块：约 800～1500 Token；
- 仅对强制拆开的连续正文保留约 10%～15% 的句子级重叠。

中文、代码、表格和模型差异会改变实际分布，最终参数必须由真实查询集决定。

### 14.3 默认使用 Parent-Child

小块负责找到准确位置，父块负责提供完整章节或条款组。召回结果按父块去重，必要时再扩展相邻单元。表格、FAQ、代码等类型使用各自专用父子关系，不强行套用段落规则。

### 14.4 混合检索优先于无限缩小 Chunk

专有名词、编号、金额、错误码和产品型号往往更依赖关键词检索；自然语言改写更适合稠密向量。与其不断缩小块来追求向量精度，不如先把 BM25/稀疏检索、元数据过滤、向量召回和重排组合好。

### 14.5 高级策略按失败类型引入

- 大量块存在指代不清，再考虑上下文化切分或 Late Chunking；
- 无结构转录稿主题混杂，再在结构节点内部增加语义边界；
- 用户问法与文档措辞差异明显，再增加问题生成索引；
- 事实密集且需要极细粒度召回，再尝试命题索引；
- 全局总结问题占比高，再增加章节摘要或层次聚合；
- 查询粒度差异巨大，再考虑动态组装或多粒度索引。

这种顺序的好处是，每项复杂度都对应一个可测量的失败模式。系统不是因为“高级策略看起来先进”而变复杂，而是因为基础方案在特定查询上已经留下了清楚证据。

## 十五、几个常见但代价高昂的误区

### 15.1 “Chunk 越小，召回越准”

小块通常主题更聚焦，但也更容易丢失主体、条件和结论。向量命中一句话不等于它能独立支持答案。应联合观察召回和父块展开后的答案质量。

### 15.2 “上下文窗口很长，所以可以不切”

长上下文解决的是模型能够接收多少内容，不等于检索器能准确找到内容，也不等于模型能稳定关注埋在中间的证据。全量塞入还会增加延迟、成本、噪声和权限风险。

### 15.3 “Overlap 越大越保险”

Overlap 会把边界风险转换成成本和重复风险。真正应该修复的是结构边界、父级上下文和查询时展开，而不是让每个块携带大量邻居副本。

### 15.4 “语义切分一定比规则切分高级”

可靠标题、合同条款和表格结构是作者或业务系统提供的强证据，通常比相邻向量相似度更可信。模型语义应该补充结构缺口，而不是覆盖确定性结构。

### 15.5 “只要检索命中了正确文档就算成功”

正确文档可能有上百页。如果命中的块不含答案，或者把条件与结论拆开，生成模型仍会失败。评估标注必须落到证据跨度。

### 15.6 “换 Embedding 模型不需要重新评估切分”

不同模型的长度上限、tokenizer 和语义表达都不同。原先最优的块大小、语义阈值与 Top-K 可能不再成立。模型迁移必须与切分、索引和重排一起回归。

## 十六、上线前检查清单

### 文档与结构

- [ ] 切分输入保留标题、段落、条款、表格、代码等结构
- [ ] 解析失败或低置信度区域有明确标记和回退策略
- [ ] 标题、表头、列表引导句、脚注不会与主体静默分离
- [ ] 每个块都能定位到原文和具体来源范围

### 边界与长度

- [ ] 使用目标模型 tokenizer，而不是只按字符估算
- [ ] 所有输入都在 Embedding 和 Reranker 限制内
- [ ] 不存在静默截断
- [ ] Overlap 只用于必要场景，并监控索引膨胀率
- [ ] 超短、超长、空块和孤立标题比例可见

### 检索与生成

- [ ] 明确区分索引单元与生成单元
- [ ] Parent-Child 或邻接展开有去重和 Token 预算
- [ ] 关键词、向量、过滤与重排共同评估
- [ ] 表格、代码、FAQ、对话使用内容类型专用策略
- [ ] 生成上下文中的重复证据得到控制

### 数据治理

- [ ] Chunk ID、父子关系和来源 ID 稳定
- [ ] 切分器、tokenizer、模型和提示词全部版本化
- [ ] ACL 在合并、召回和上下文展开的每一步都生效
- [ ] 文档更新、撤回、过期和删除能传播到全部派生索引
- [ ] 摘要、命题和生成问题不会被冒充为原始证据

### 评估与运维

- [ ] 查询集来自真实业务，并标注到证据跨度
- [ ] 覆盖边界、例外、表格、多跳、版本和拒答问题
- [ ] 同时衡量检索、答案、引用、延迟和成本
- [ ] 新策略通过影子索引或 A/B 测试验证，可随时回滚
- [ ] 指标按文档类型、语言、租户和切分版本分层观察

## 结语

RAG 文档切分没有脱离业务的最优算法，只有针对特定查询分布、文档结构和系统约束的更优折中。

如果只保留一套原则，我会选择下面五条：

1. **结构优先于长度，长度负责兜底；**
2. **索引单元与生成单元应当解耦；**
3. **Overlap 用来补偿少量边界风险，不用来替代结构理解；**
4. **模型生成的上下文、命题和摘要只做检索指针，原文才是证据；**
5. **任何策略都必须通过真实查询、证据跨度、端到端答案和单位成本共同验证。**

一个成熟的切分系统，不是把所有文档切成整齐的同样大小，而是知道哪些边界不能破坏、哪些上下文可以按需展开、哪些复杂度确实值得付费，以及出了问题之后如何回到原文解释每一次决定。

当 RAG 回答不理想时，也不要立刻把 `chunk_size` 从 500 改成 800。先判断失败属于哪一类：正确证据没有被索引、索引块无法被发现、召回块缺少回答上下文、重复块挤占候选，还是生成模型没有使用已有证据。只有把失败定位清楚，切分优化才是工程，而不是调参玄学。
