很多 RAG 教程会从“把文档读出来”直接跳到“切块、Embedding、入库”，仿佛文档解析只是调用一个 `loader.load()`。真正做过项目后才会发现：**检索效果的上限，往往在向量化之前就已经被文档解析决定了。**

同一句话如果被错误地拼到另一栏，模型理解的就是错误上下文；表格如果只剩一串数字，检索到了也无法回答；标题层级一旦丢失，切块后的段落就不知道自己属于哪一章；扫描 PDF 没有经过 OCR，后续流程得到的甚至可能只是空字符串。

本文不绑定某个 RAG 框架，而是从工程视角搭建一条可以落地的文档处理流水线。我们会重点处理 PDF、Word 和 Excel，同时说明扫描件、复杂版面、公式、图片、合并单元格、旧格式、超大文件、密码文件、乱码、损坏文件等棘手情况。

> 本文的目标不是寻找一个“万能解析库”，而是教你建立一套可判断、可降级、可验证、可追溯的处理方法。现实世界不存在对所有文档都完美的解析器，但可以存在一条遇到异常不会悄悄产出垃圾数据的流水线。

## 一、先把边界说清楚：文档解析到底负责什么

一条比较完整的 RAG 文档处理链路可以写成：

```text
文件接入与安全检查
→ 文件识别与解析路由
→ 内容提取（文本、表格、图片、OCR、版面坐标）
→ 基础规范化
→ 文档结构重建
→ 结构感知去噪与去重
→ 语义单元划分
→ 切块
→ 元数据补全
→ 质量校验
→ 可追溯输出
→ 向量化与索引
```

这条链路中最容易犯的错误，是让某个步骤替其他步骤做决定。例如，解析器一边读取 PDF，一边删除它认为没用的短句；切块器拿到纯文本后，猜测哪一行是标题；Embedding 前临时用正则清洗空白，顺手破坏了表格。

正确做法是给每个阶段划定职责：

| 阶段 | 应该做什么 | 不应该做什么 |
| --- | --- | --- |
| 文件接入 | 鉴权、限流、保存原件、计算哈希、记录来源 | 根据扩展名盲目信任文件类型 |
| 内容提取 | 尽可能忠实地提取文本、坐标、样式、表格和图片 | 总结、改写、删除“看起来没用”的内容 |
| 基础规范化 | 统一编码、换行、Unicode、空白和可安全修复的断词 | 在不知道结构时大量使用正则删内容 |
| 结构重建 | 恢复章节、段落、列表、表格、图片说明和阅读顺序 | 为了好看而改变原文含义 |
| 去噪 | 利用结构和统计信息删除页眉页脚、重复水印等 | 删除免责声明、单位、表头等业务信息 |
| 切块 | 在语义边界内控制块大小，并保留上下文 | 机械地每 N 个字符截断 |
| 质量校验 | 检查丢失、错序、乱码、表格破坏和可回溯性 | 只检查程序是否返回 200 |
| 向量化与索引 | 把合格语义块交给检索系统 | 回头修补解析阶段已经损坏的文本 |

本文重点截止到“可追溯输出”。向量数据库选型、Embedding 模型和召回排序属于下游，只在最后说明接口。

## 二、不要让每种文件输出一种格式

如果 PDF 解析器返回字符串、Word 解析器返回段落数组、Excel 解析器返回 DataFrame，后面的去噪和切块会充满文件类型判断。工程上应该先定义一个统一的中间文档模型。

最小可用模型可以包含三层：

```python
from dataclasses import dataclass, field
from typing import Any, Literal

BlockType = Literal[
    "title", "heading", "paragraph", "list_item",
    "table", "image", "caption", "formula", "footnote"
]

@dataclass
class SourceRef:
    file_id: str
    page: int | None = None
    sheet: str | None = None
    cell_range: str | None = None
    bbox: tuple[float, float, float, float] | None = None

@dataclass
class Block:
    block_id: str
    type: BlockType
    text: str
    source: SourceRef
    heading_path: list[str] = field(default_factory=list)
    metadata: dict[str, Any] = field(default_factory=dict)

@dataclass
class ParsedDocument:
    document_id: str
    filename: str
    mime_type: str
    blocks: list[Block]
    metadata: dict[str, Any]
    warnings: list[str] = field(default_factory=list)
```

这里最重要的不是类名，而是几个原则：

1. **内容和来源绑定。** 每个块都知道自己来自第几页、哪个工作表或哪个单元格区域。
2. **文本和结构并存。** 不要只保存最终纯文本，块类型、标题路径、坐标和样式证据也要保存。
3. **警告是正式输出。** OCR 置信度低、公式未识别、文件有密码，都不能只写进服务器日志。
4. **原始层与处理层分离。** 最好同时保留 `raw_text` 与清洗后的 `text`，否则出现误删时无法复盘。
5. **ID 必须稳定。** 文档 ID 可以由租户、来源 ID 和文件哈希组成；块 ID 应由文档 ID、位置和处理版本稳定生成，避免重跑后整库重复。

一个块进入向量库后，至少应该能回答：“它来自哪个文件、哪个版本、哪一页、哪个章节，原文在哪里？”如果回答不了，就还不能称为可追溯。

## 三、第一关：文件接入与安全检查

文档还没解析，工程问题就已经开始了。

### 3.1 不要只看扩展名

用户可以把 `invoice.exe` 改名为 `invoice.pdf`，也可能把一个真实的 XLSX 错误命名为 `.xls`。扩展名只能作为提示，至少要结合：

- 文件签名（magic bytes）；
- MIME 类型探测；
- 容器结构检查；
- 解析器试读结果。

PDF 通常以 `%PDF-` 开头；DOCX、XLSX、PPTX 本质上是 ZIP 容器，但“以 ZIP 开头”不能证明它就是 Office 文档，还要检查 `[Content_Types].xml` 和内部目录。

路由时应记录“扩展名判断”和“真实类型判断”的差异。类型不一致不一定要拒绝，但不能默默处理。

### 3.2 接入阶段必须做的检查

- 限制单文件大小、页数、工作表数、解压后总大小和嵌套深度；
- 计算 SHA-256，用于去重、缓存和审计；
- 原始文件写入只读对象存储，处理任务只使用副本；
- 文件名做净化，禁止目录穿越，不使用用户文件名作为磁盘路径；
- 每个解析任务设置 CPU、内存和执行超时；
- Office 宏、嵌入对象和外部链接默认不执行；
- 高风险文件在隔离容器中处理，并进行恶意文件扫描；
- 记录上传者、租户、权限标签、来源系统和采集时间。

### 3.3 几种必须显式分流的文件

| 情况 | 建议处理 |
| --- | --- |
| 加密或密码保护 | 状态设为 `needs_password`，由安全通道提供密码；禁止无限重试 |
| 损坏但可部分读取 | 输出已恢复内容，同时标记页码/工作表缺失和解析警告 |
| 0 字节或只有空白页 | 拒绝进入索引，保留失败原因 |
| ZIP 炸弹或异常压缩比 | 接入层直接隔离，不交给解析器 |
| `.doc`、`.xls` 等旧格式 | 在隔离环境用 LibreOffice 等转换，保留原件和转换件 |
| 文件正在上传或同步 | 等待大小和修改时间稳定后再处理，避免读到半个文件 |
| 同文件重复上传 | 用哈希命中缓存，但仍要重新计算权限和业务元数据 |

## 四、第二关：文件识别与解析路由

“一个 PDF 解析器处理全部 PDF”几乎一定会失败。路由不应只按文件后缀，还要按文档特征选择策略。

### 4.1 PDF 至少分成四类

1. **数字原生 PDF：** 能选择文字，通常有可靠文本层。
2. **纯扫描 PDF：** 每页主要是一张图片，需要 OCR。
3. **混合 PDF：** 部分页有文本层，部分是扫描件，必须逐页判断。
4. **有文本层但不可用：** 能提取文字，却出现乱码、重复字、错误顺序或透明 OCR 层错位。

逐页统计字符数、图片覆盖率、字体信息和不可打印字符比例，比“整份文件提取结果是不是空”更可靠。例如一份 100 页合同可能只有签字页是扫描件，整份 OCR 会浪费资源，还可能破坏原本正确的文本。

### 4.2 Word 与 Excel 也要分流

- `.docx` 与 `.xlsx` 是现代 OOXML 容器，可以直接解析；
- `.doc` 与 `.xls` 是旧二进制格式，不能用 `python-docx` 或 `openpyxl` 硬读；
- `.xlsb` 是二进制工作簿，需要专用读取器；
- CSV 不是 Excel 工作簿，没有工作表、样式和合并单元格，还存在编码和分隔符检测问题；
- 带宏的 `.docm`、`.xlsm` 可以读取内容，但不要执行宏；如需保留宏，转换和保存时必须谨慎。

### 4.3 路由要支持“主解析器 + 回退解析器”

生产系统中可以给每种类型配置多级策略：

```text
数字 PDF：版面解析器 → 普通文本解析器 → OCR 回退
扫描 PDF：图像预处理 → OCR → 版面重建
DOCX：OOXML 结构解析 → LibreOffice 转 PDF 回退
XLSX：工作簿结构解析 → LibreOffice 渲染/导出回退
未知文件：隔离 → 人工确认，不进入索引
```

回退不是捕获所有异常后随便换一个库。每次回退都要记录触发原因、使用的解析器、版本、耗时和输出质量。

## 五、PDF：最常见，也最容易“看起来成功”

PDF 描述的是“字符画在页面的哪个位置”，不天然包含段落、标题或表格语义。同一份肉眼完全正常的 PDF，内部字符顺序可能是乱的。

### 5.1 数字 PDF：先保留坐标，再谈纯文本

使用 PyMuPDF 时，`page.get_text("text")` 适合快速预览；用于 RAG 工程，更推荐提取 block、word 或 dict，因为它们保留坐标和样式信息。

```python
import fitz

doc = fitz.open("example.pdf")

for page_index, page in enumerate(doc):
    blocks = page.get_text("dict", sort=False)["blocks"]
    for block in blocks:
        bbox = block.get("bbox")
        # 先保存原始块、坐标和 span 样式，阅读顺序在后续阶段判断
```

`sort=True` 可以按大致的“从上到下、从左到右”排序，但它不是多栏排版的万能答案。双栏论文如果按横向坐标穿插排序，可能变成左栏第一行、右栏第一行、左栏第二行……正确处理需要：

1. 找出跨整页的标题、摘要和页脚；
2. 根据文本块的横向分布识别栏位；
3. 栏内按纵坐标排序；
4. 再按页面阅读规则拼接各栏；
5. 对跨栏图片、表格和标题单独处理。

复杂杂志、财报和宣传册没有通用规则，应使用版面检测模型，并把低置信度页面送入人工抽检。

### 5.2 如何判断某页是否需要 OCR

不要用单一阈值。可以综合以下信号：

- 页面提取字符数很少，但页面存在大面积图片；
- 图片面积占页面面积比例很高；
- 文本中不可打印字符、乱码或重复字符比例异常；
- 页面肉眼有文字，提取结果却为空；
- 已有 OCR 文本层与图像位置明显不一致。

混合文档应逐页 OCR。对于已有正确文本层的页面，重复 OCR 可能引入错字；对于已有损坏 OCR 层的页面，则需要明确使用“重做 OCR”策略。

OCR 前常见预处理包括：

- 方向纠正：处理整页旋转 90°、180°；
- 倾斜校正：处理扫描时轻微歪斜；
- 去噪和背景清理；
- 提升对比度、二值化；
- 合理放大低分辨率图片；
- 按页面语言选择 OCR 语言包。

```bash
# 示例：中英文混合，自动旋转并校正倾斜
ocrmypdf -l chi_sim+eng --rotate-pages --deskew input.pdf output.pdf
```

不要对含彩色照片、印章或浅色批注的文档盲目“去背景”，预处理可能把有效内容一起擦掉。原始页图、预处理图和 OCR 结果应能够对照。

### 5.3 OCR 的结果不能只看“识别出了多少字”

至少检查：

- OCR 平均置信度和低置信度词占比；
- 数字、金额、日期、编号等关键字段的格式；
- 中英文混排是否出现空格异常；
- `0/O`、`1/l/I`、负号/破折号、全角/半角是否混淆；
- 页码和文字框坐标是否对应；
- 表格线是否导致字符被切断；
- 印章、手写体和竖排文字是否需要专用模型。

身份证号、合同金额、药品剂量等高风险字段，不能依赖普通 OCR 自动通过。应加字段规则校验或人工复核。

### 5.4 PDF 表格：别把视觉上的表格等同于二维数组

表格大致分为：

- 有完整边框的规则表格；
- 只有横线或没有边框的对齐表格；
- 合并单元格、多级表头；
- 单元格内多行、列表或图片；
- 跨页表格；
- 旋转表格；
- 扫描表格。

处理表格时应同时保存：

1. 原始页面区域和坐标；
2. 单元格矩阵；
3. 合并关系；
4. 表头层级；
5. 表格标题、脚注和单位；
6. Markdown/HTML 等便于模型理解的文本表示。

跨页表格要识别重复表头，合并连续页面的主体行，但不能把两个恰好列数相同的表格误合并。可以结合表格标题、列边界、表头相似度、页码连续性和“续表”等标记判断。

扫描表格通常需要“表格检测 → 单元格结构识别 → 单元格 OCR”，不能只对整页做普通 OCR。无边框表格或财报复杂表格应保留截图作为证据，并允许视觉模型作为回退，但不要让视觉模型无依据地补全缺失数字。

### 5.5 图片、公式、脚注和批注怎么办

- **图片：** 保存图片本体、所在页、坐标、附近标题和正文引用；装饰图可过滤，业务图应生成说明或使用多模态模型理解。
- **图表：** 图例、坐标轴、单位和数据来源必须与图片绑定。仅生成一句图片描述通常不足以回答精确数值问题。
- **公式：** 普通文本提取容易丢失上下标和结构。需要公式识别时，应保存 LaTeX/MathML、原图和页码；不需要精确公式检索时，也不要擅自把公式改写成自然语言结论。
- **脚注：** 脚注文本应保留，并通过引用标记与正文关联，不能简单当页脚删除。
- **高亮与批注：** 在审阅、法务和知识管理场景中可能非常重要，应作为 annotation block 保存。
- **表单字段：** PDF 表单中的值可能不在普通文本流里，需要读取 AcroForm 字段。

### 5.6 PDF 常见故障速查

| 现象 | 常见原因 | 处理策略 |
| --- | --- | --- |
| 能复制但提取乱码 | 字体缺少 Unicode 映射、自定义编码 | 换解析器、检查字体映射，必要时对页面 OCR |
| 字符顺序颠倒 | 内容流顺序与视觉顺序不同 | 使用坐标重排，不依赖纯文本顺序 |
| 每个字重复两次 | 可见文字与隐藏 OCR 层同时被提取 | 检测重叠 bbox 和重复文本，选择可信层 |
| 双栏内容串行 | 简单上下左右排序失败 | 识别栏位后分栏排序 |
| 页眉混入正文 | 每页重复区域未识别 | 结合位置、跨页频率和文本相似度去噪 |
| 表格变成一列数字 | 普通文本提取丢失单元格关系 | 使用表格结构提取并保存表头 |
| 某几页为空 | 混合型 PDF 中存在扫描页 | 逐页判断并局部 OCR |
| 打不开或只读到部分页 | 加密、交叉引用表损坏、增量保存异常 | 请求密码、尝试修复，标记未恢复页 |
| 文件极慢或内存暴涨 | 超大图片、页面对象复杂、恶意文件 | 分页处理、限制资源、设置超时并隔离 |

## 六、Word：结构比 PDF 好，但绝不只是 paragraphs

DOCX 内部保存了段落、样式、表格和关系信息，理论上更适合恢复层级。但如果只遍历 `document.paragraphs`，会漏掉或打乱很多内容。

### 6.1 按文档顺序读取段落和表格

较新的 `python-docx` 可以使用 `iter_inner_content()` 按顺序遍历顶层段落与表格：

```python
from docx import Document
from docx.table import Table
from docx.text.paragraph import Paragraph

document = Document("example.docx")

for item in document.iter_inner_content():
    if isinstance(item, Paragraph):
        pass  # 读取文本、样式、run、超链接等
    elif isinstance(item, Table):
        pass  # 读取单元格、合并关系和嵌套内容
```

只读取 `document.paragraphs` 会漏掉表格中的文本；先读全部段落、再读全部表格又会破坏原始顺序。

### 6.2 标题层级不能只看字体大小

优先证据顺序可以是：

1. 内置或自定义标题样式；
2. 大纲级别（outline level）；
3. 编号规则；
4. 字体、加粗、段前段后间距等视觉特征；
5. 文本模式，如“第一章”“1.2.3”。

企业模板经常把标题样式改名，或把所有内容都设成“正文”后手工加粗。因此要保存“为什么判定为标题”的证据和置信度。不要仅凭“短且加粗”判断，否则表格中的字段名会被误当成章节标题。

### 6.3 Word 列表和编号的坑

`1.`、`（一）`、项目符号有时不是段落文本，而是由编号定义生成。只读 `paragraph.text` 可能看不到编号。准确恢复需要解析 OOXML 中段落的编号属性、抽象编号定义、级别和起始值。

还要处理：

- 编号中途重新开始；
- 多级列表跨段落；
- 自定义编号格式；
- 列表项中嵌套表格或图片；
- 看起来像列表、实际只是手打符号的段落。

切块时列表项通常应保持完整；很短的连续列表可以和它的引导段落放在同一块中。

### 6.4 Word 表格不一定规整

需要考虑：

- 横向和纵向合并单元格；
- 嵌套表格；
- 单元格中多个段落、列表、图片；
- 表格跨页时重复标题行；
- 表格前后的标题、注释和单位；
- 仅用于页面排版、并非业务数据的无边框表格。

不要直接把所有单元格用 `|` 拼接。如果一个合并表头覆盖三列，应把它传播为列的层级上下文；如果表格用于双栏排版，则应该恢复为普通内容流，而不是输出假表格。

### 6.5 容易被漏掉的 Word 内容

- 页眉、页脚和不同 section 的首页/奇偶页设置；
- 文本框和浮动形状中的文字；
- 内嵌图片与图片说明；
- 超链接真实地址；
- 脚注、尾注、批注；
- 修订记录中的插入和删除；
- 目录、交叉引用、页码等域代码；
- 嵌入的 Excel、PDF 等 OLE 对象；
- 数学公式；
- 隐藏文字。

`python-docx` 对正文、顶层表格和内联图片很方便，但不是对 OOXML 所有特性的完整封装。遇到文本框、修订、脚注、复杂编号和浮动对象时，通常需要读取底层 XML，或使用 LibreOffice 渲染成 PDF 作为视觉回退。

特别注意：**转成 PDF 可以保住视觉布局，却可能损失 Word 原本清晰的语义结构。** 因此更好的办法是同时保留 DOCX 结构解析结果与渲染结果，用后者检查顺序和遗漏，而不是一开始就全部转 PDF。

### 6.6 修订、删除内容到底要不要索引

没有统一答案，必须由业务规则决定：

- 已接受的正式制度：通常只索引最终可见版本；
- 合同审阅：可能要同时保留插入、删除和批注；
- 法务取证：任何隐藏或修订内容都不能静默丢弃；
- 普通知识库：删除内容通常不进入检索，但应记录文档存在修订。

这属于接入策略，不应由解析库默认行为替你决定。

### 6.7 `.doc`、密码和损坏文件

`.doc` 不是 `.docx`，不能通过改扩展名解决。常见方案是在隔离环境中用 LibreOffice 无界面模式转换为 DOCX 或 PDF：

```bash
libreoffice --headless --convert-to docx --outdir converted legacy.doc
```

转换后要比较页数、段落数量和文件大小，保留转换日志。密码文件进入等待状态；损坏文档可以尝试由 Office/LibreOffice 修复，但修复件必须与原件分别保存。

## 七、Excel：解析的不是“文字”，而是一个小型数据系统

Excel 的核心问题不是把单元格读出来，而是理解工作簿结构。一个工作表里可能有封面、说明、多个独立表格、公式、图表和隐藏区域。把整张表 `astype(str)` 后拼成文本，通常既浪费 Token，又丢失语义。

### 7.1 先做工作簿级盘点

打开工作簿后先记录：

- 工作表名称、顺序、显示/隐藏/very hidden 状态；
- 实际有值区域，而不是被格式污染的 `max_row`、`max_column`；
- 合并单元格范围；
- 冻结窗格、筛选、命名区域和 Excel 表对象；
- 公式、缓存值、错误值和外部链接；
- 批注、图片、图表、透视表；
- 文件日期系统、区域格式和单位。

```python
from openpyxl import load_workbook

# 大文件优先 read_only；data_only=False 保留公式文本
formula_wb = load_workbook("example.xlsx", read_only=True, data_only=False)

# 如需公式上次计算的缓存值，可另开一次；openpyxl 不负责计算公式
value_wb = load_workbook("example.xlsx", read_only=True, data_only=True)
```

`data_only=True` 不会计算公式，只会读取 Excel 上次保存的缓存结果。如果文件由某些程序生成、从未在 Excel 中重算，缓存可能为空或过期。因此生产模型最好同时保留：

```json
{
  "formula": "=SUM(B2:B10)",
  "cached_value": 12345.67,
  "calculation_status": "cached_not_verified"
}
```

### 7.2 先识别表格区域，再解释行列

一个 Sheet 不等于一张表。可以通过以下线索划分区域：

- 连续非空单元格形成的矩形区域；
- 空行、空列作为候选分隔；
- Excel Table 和命名区域；
- 合并的大标题；
- 样式、边框、填充色的变化；
- 重复表头；
- 公式引用关系。

对于每个候选区域，再判断：

1. 哪几行是标题和说明？
2. 表头占一行还是多行？
3. 是否存在行标题和分组小计？
4. 单位在表头、标题还是单独单元格？
5. 空单元格表示缺失、沿用上值，还是合并单元格的从属位置？

### 7.3 多级表头和合并单元格

例如：

| 地区 | 2025 年 |  | 2026 年 |  |
| --- | --- | --- | --- | --- |
|  | 收入 | 成本 | 收入 | 成本 |

不能只取最后一行表头，否则会得到两个“收入”和两个“成本”。应展开为完整列路径：

```text
地区
2025 年 / 收入
2025 年 / 成本
2026 年 / 收入
2026 年 / 成本
```

合并单元格通常只有左上角有值。展开时可以为结构计算传播值，但要保留原始合并范围，避免把展示上的合并误解成每个单元格都填写了同一数据。

### 7.4 表格如何转换成适合 RAG 的文本

小表可以整体转为 Markdown；大表不应整张塞进一个块。更稳妥的做法是“表格上下文 + 表头 + 若干数据行”：

```text
工作表：华东区销售
表格：2026 年季度收入（单位：万元）
列：城市 | Q1 | Q2 | Q3 | Q4
行：杭州 | 120 | 135 | 140 | 160
来源：Sheet「销售汇总」!A4:E18
```

每个行块都带完整表头和单位。对于“某地区四个季度趋势”这类问题，可以按业务主键分组多行；对于横向极宽表格，可按列主题拆分，但主键列要复制到每个子块。

不要把每个单元格独立向量化。脱离行、列、单位和工作表上下文后，单元格 `120` 没有任何可检索意义。

### 7.5 Excel 中最棘手的情况

| 情况 | 风险 | 建议 |
| --- | --- | --- |
| 隐藏工作表/行/列 | 可能是内部计算，也可能是重要数据 | 按业务策略决定是否索引，默认记录但不静默公开 |
| 公式缓存为空 | `data_only=True` 得到 `None` | 保存公式，必要时用受控 Office 引擎重算 |
| 外部链接 | 结果依赖另一个文件 | 禁止自动访问不可信地址，标记依赖未解析 |
| 日期变成数字 | Excel 序列日期与普通数字混淆 | 结合单元格格式和工作簿日期系统解释 |
| `max_row` 巨大 | 用户给整列套过格式 | 根据真实非空单元格和边界估算有效区域 |
| 一个 Sheet 多张表 | 整表拼接导致语义混杂 | 先做区域检测和标题关联 |
| 透视表/图表 | 只读源单元格会漏掉展示语义 | 保存图表标题、系列、范围；必要时渲染截图 |
| 图片内有表格 | 单元格解析完全看不到 | 图片检测后走 OCR/视觉表格流程 |
| `.xlsb`/`.xls` | openpyxl 不支持 | 使用专用库或隔离转换 |
| CSV 乱码/错列 | 编码、分隔符、引号、换行不确定 | 探测后抽样确认，保存原始字节和解析参数 |
| 超大工作簿 | 内存溢出、处理时间过长 | 只读流式遍历，按 Sheet/区域分任务 |
| 错误值 `#N/A` 等 | 转字符串后被当普通内容 | 保留错误类型并标记计算状态 |

### 7.6 Excel 权限边界尤其重要

工作簿中可能有隐藏工资表、成本底稿或个人信息。解析系统不能因为“文件对用户可见”就默认所有工作表都可进入公共知识库。权限标签应能下沉到 sheet、表格甚至行级块，索引和检索阶段都必须执行过滤。

## 八、基础规范化：只做低风险、可逆的清理

基础规范化发生在结构重建前，因此必须克制。适合处理的内容包括：

- 统一为 Unicode；
- 规范 `\r\n`、`\r` 为 `\n`；
- 处理不间断空格、零宽字符和控制字符；
- 连续普通空格按语言规则收敛；
- 统一全角/半角时要有业务开关；
- 修复 PDF 行末的明确断词；
- 保留原文与规范化文本的映射。

### 8.1 不要粗暴删除所有换行

换行可能表示：

- PDF 视觉折行；
- 新段落；
- 标题结束；
- 列表项边界；
- 表格单元格内换行；
- 代码或诗歌中的有效格式。

是否合并要结合块类型、缩进、行距、标点和下一行位置。英文中的 `inter-\nnational` 可能是断词，`state-of-\nthe-art` 却不能简单删除所有连字符。中文通常没有西文断词，但每行一个短句可能是 OCR 或排版结果。

### 8.2 Unicode 规范化也不是无脑操作

NFKC 会把某些兼容字符折叠，适合搜索归一化，却可能改变数学符号或业务代码。建议保留：

- `raw_text`：忠实原文；
- `display_text`：适合展示和引用；
- `search_text`：用于检索归一化。

这样既能提高召回，又不会在回答引用时展示被改写的原文。

## 九、结构重建：把“文本块”还原成“文档”

结构重建的目标是形成一棵文档树，而不是生成漂亮 Markdown：

```text
文档
├─ 标题
├─ 第一章
│  ├─ 1.1 小节
│  │  ├─ 段落
│  │  ├─ 列表
│  │  └─ 表格
│  └─ 1.2 小节
└─ 附录
```

### 9.1 标题识别应融合多种证据

- PDF：字体大小、粗体、位置、上下间距、编号模式、跨页一致性；
- Word：样式、大纲级别、编号定义；
- Excel：合并区域、样式、位置、命名区域和表格标题；
- 通用：文本长度、标点、与后续内容的关系。

标题检测错一次，后面许多块的 `heading_path` 都会错。因此要设置信心阈值：高置信度自动通过，中置信度使用规则或模型复核，低置信度保留为普通段落并记录告警。

### 9.2 阅读顺序不是简单排序

排序需要同时处理：

- 多栏正文；
- 跨栏标题和图片；
- 侧边注释；
- 表格与说明文字；
- 脚注；
- 浮动文本框；
- 横向页面和旋转区域。

结构重建时应保留原始顺序和重建顺序。两者差异过大时触发抽检，而不是静默覆盖。

### 9.3 跨页段落如何合并

上一页末尾和下一页开头可能是同一段。可以根据以下信号判断：

- 上一页最后一行没有终止标点；
- 下一页第一行不是标题、列表或表头；
- 字体、缩进和行距一致；
- 页面边缘位置符合正文区域；
- 不存在分页符或章节边界。

合并后仍应保存两个 source span，让引用能够定位到两页。

## 十、结构感知去噪：噪声不是“短文本”

去噪必须放在结构已经基本恢复之后。典型噪声包括：

- 每页重复的页眉、页脚和页码；
- 重复水印；
- 扫描产生的边缘字符；
- PDF 中重叠的重复文字层；
- 目录点线和无意义装饰符；
- Excel 中大面积空样式区域；
- 转换工具插入的固定提示。

### 10.1 页眉页脚的稳妥识别方法

不要写死“页面顶部 10% 全删”。可以组合：

1. 位于多数页面相似位置；
2. 文本完全相同，或只在页码、日期、章节名处变化；
3. 字体和尺寸稳定；
4. 与正文有明显间距；
5. 在连续页面重复出现。

首页标题、章节页标题、合同编号和保密级别也可能位于顶部，不能因位置相同就删除。更安全的做法是先标记为 `running_header`，索引时按业务需要过滤，而不是从数据中物理删除。

### 10.2 去重分三个层次

- **文件级去重：** 文件哈希完全相同；
- **版本级近重复：** 同一文档小幅修改，需要保留版本关系；
- **块级重复：** 模板条款、导航、页眉在多个文档重复。

块级重复不能只凭向量相似度删除。不同合同中的相同条款可能都需要保留各自来源和权限。更好的做法是内容指纹归并、来源列表保留，并在检索阶段控制重复结果。

## 十一、语义单元划分：切块前还有一步

解析块不一定就是适合切块的单元。语义单元是不能轻易拆开的最小内容，例如：

- 一个标题及其紧随的说明；
- 一个完整段落；
- 一个列表项；
- 一条表格记录连同表头；
- 图片与其说明；
- 公式与变量解释；
- 脚注与它引用的正文。

先把文档变成语义单元，再组合成 Chunk，比对纯文本递归分隔稳定得多。

## 十二、切块：不是“每 500 字切一刀”

切块需要在两个目标之间平衡：

- 块太小：语义不完整，检索结果缺少回答所需上下文；
- 块太大：主题混杂，向量表达被稀释，召回后还浪费上下文窗口。

### 12.1 推荐的结构感知切块顺序

1. 章节边界优先；
2. 段落、列表、表格行等语义单元不可随意拆；
3. 在 Token 预算内合并相邻且同主题的单元；
4. 单个单元超长时，再使用句子边界或专用规则拆分；
5. 给每个块补充标题路径和必要上下文；
6. 生成稳定 chunk ID 和来源跨度。

### 12.2 用 Token 而不是字符估算

模型接收的是 Token。中英文、代码和数字的字符/Token 比例不同，固定字符数只能作为粗略近似。切块器应使用与下游模型接近的 tokenizer。

不存在适合所有项目的固定大小。可以从以下区间开始实验：

- 事实型问答：约 300～600 Token；
- 解释型、制度型内容：约 500～1000 Token；
- Parent-Child 检索：子块约 200～400 Token，父块约 1000～2000 Token。

这些不是标准答案。最终要用真实问题集评估召回率、答案完整度和引用精度。

### 12.3 Overlap 不是越多越好

重叠适合弥补普通段落边界，但会增加索引量和重复召回。建议：

- 只在被强制拆开的连续正文中使用；
- 不对表格行机械重叠；
- 标题路径通过元数据或前缀补充，不靠重复正文；
- 重叠长度随句子边界调整，而不是固定截取半句话。

### 12.4 不同内容要用不同切法

| 内容 | 推荐策略 |
| --- | --- |
| 普通章节正文 | 标题路径 + 段落组合，超限按句子拆 |
| FAQ | 问题与完整答案不可拆开 |
| 合同条款 | 以条、款、项为边界，保留上级条款标题 |
| 技术手册 | 操作步骤、前置条件和警告尽量同块 |
| 表格 | 表头与数据行绑定，按业务主键或行组拆 |
| 代码 | 按函数、类或语法节点拆，保留文件路径 |
| 对话记录 | 按轮次和主题窗口拆，保留说话人和时间 |
| 图片/图表 | 图片说明、OCR、附近引用和资源 ID 同块 |

### 12.5 一个合格 Chunk 应该长什么样

```json
{
  "chunk_id": "doc_123:p12-13:c04:v3",
  "text": "……可用于展示和引用的正文……",
  "search_text": "……用于检索的规范化文本……",
  "heading_path": ["第三章 风险管理", "3.2 审批流程"],
  "content_types": ["paragraph", "list_item"],
  "source_spans": [
    {"page": 12, "bbox": [72, 110, 520, 760]},
    {"page": 13, "bbox": [72, 60, 520, 180]}
  ],
  "document_version": "sha256:...",
  "parser_version": "pipeline-2026.08",
  "acl": ["department:legal"],
  "warnings": []
}
```

## 十三、元数据：少了它，检索系统迟早失控

推荐至少保存：

- 文档 ID、文件名、文件哈希、版本号；
- 来源 URL/对象存储位置、上传者、采集时间；
- MIME 类型、原始扩展名、文件大小；
- 页码、工作表、单元格区域、坐标；
- 标题路径、块类型、语言；
- 解析器、OCR 引擎、处理配置和版本；
- 权限标签、租户、保密级别；
- OCR 置信度、结构置信度和警告；
- 生效时间、失效时间、业务状态。

不要把所有元数据都拼进 Embedding 文本。文件名、标题和必要表头可以作为语义上下文；哈希、内部路径、权限标签等用于过滤和审计即可。

## 十四、质量校验：解析成功不等于内容正确

一个解析任务返回成功，只能说明程序没有崩溃。生产环境至少要做四类检查。

### 14.1 完整性检查

- 输入页数与处理页数是否一致；
- 每页是否产生了文本、图片、表格或“确认空白”的结论；
- Word 的段落、表格、图片数量是否异常减少；
- Excel 的工作表和候选表格区域是否全部得到处理；
- 原始文本量与输出文本量比例是否突然异常。

### 14.2 文本质量检查

- 乱码字符比例；
- 不可打印字符比例；
- 单字符重复、异常空格和错误换行；
- OCR 低置信度比例；
- 语言识别与预期是否一致；
- 金额、日期、编号等格式是否合法。

### 14.3 结构质量检查

- 标题层级是否突然从 H1 跳到 H5；
- 阅读顺序是否出现栏位穿插；
- 表格每行列数是否一致；
- 跨页表格是否正确合并；
- 列表编号是否连续；
- 图片说明是否关联到正确图片。

### 14.4 切块质量检查

- 是否存在空块、超短块和超长块；
- 块是否从半句话开始或结束；
- 表头是否与数据分离；
- 标题路径是否正确；
- 每个块是否能定位回原文；
- 权限元数据是否继承完整；
- 同一文档是否产生大量近重复块。

### 14.5 建立“黄金文档集”

不要只拿三份漂亮文件测试。至少准备：

- 单栏和双栏 PDF；
- 纯扫描、混合扫描、倾斜和旋转页面；
- 有框、无框、跨页和多级表头表格；
- 含文本框、修订、脚注、图片和嵌套表格的 Word；
- 多 Sheet、多表区、公式、合并单元格、隐藏行列和超大 Excel；
- 密码、损坏、旧格式、空文件和错误扩展名；
- 中英文混排、特殊符号和业务编号。

为黄金文档人工标注关键事实、标题树、表格区域和期望引用位置。每次升级解析器或规则都做回归测试。解析质量最终还要用真实问题衡量：关键问题能否召回正确块，答案是否能引用到正确页码。

## 十五、生产系统必须有失败分级，而不是一个 try/except

建议把处理结果分为：

| 状态 | 含义 | 后续动作 |
| --- | --- | --- |
| `success` | 通过全部硬性校验 | 可以进入索引 |
| `success_with_warnings` | 内容可用，但存在局部低置信度 | 进入索引并标记，安排抽检 |
| `needs_password` | 文件加密 | 等待安全提供密码 |
| `needs_review` | 结构或 OCR 置信度不足 | 人工复核或切换解析策略 |
| `unsupported` | 格式暂不支持 | 隔离并反馈支持范围 |
| `quarantined` | 安全风险或资源异常 | 禁止继续自动处理 |
| `failed` | 解析器错误或文件损坏 | 保留日志、可控重试 |

不要让失败文件自动重试几十次。重试只适合临时错误；确定性的格式错误应直接进入人工队列。

## 十六、性能、成本与可维护性

### 16.1 分阶段缓存

可以按“文件哈希 + 解析器版本 + 配置版本”缓存：

- 原始解析结果；
- OCR 结果；
- 结构化文档；
- Chunk 输出。

只修改切块参数时，不应重新做昂贵 OCR；升级 OCR 模型时，也不必重新上传原文件。

### 16.2 大文件要流式和分片

- PDF 按页或页组处理；
- Excel 按 Sheet 和区域流式读取；
- 图片 OCR 使用有界并发；
- 中间结果写对象存储，不把整份文档常驻内存；
- 对单页超时、单页失败和整文档失败分别处理。

并行处理后要按稳定位置重新排序，不能按任务完成时间拼接。

### 16.3 可观测性指标

建议监控：

- 各格式成功率、回退率和人工复核率；
- 每页解析耗时、OCR 耗时和成本；
- 平均字符数、块数和 Token 数；
- 空页率、乱码率、低 OCR 置信度率；
- 表格识别数量和结构异常率；
- 解析器版本变更前后的质量差异；
- 从上传到可检索的端到端延迟。

日志中不要直接打印完整敏感正文。使用 document ID、block ID 和脱敏片段定位问题。

## 十七、隐私、安全和提示注入

文档内容本身是不可信输入。除了传统文件安全，还要考虑 RAG 特有风险：

- 文档中可能写着“忽略系统指令”等提示注入内容；
- 隐藏文字、白色文字或批注可能包含恶意指令；
- 检索结果可能跨租户或跨部门泄漏；
- OCR/解析第三方 API 可能把敏感文件传到外部；
- 日志、缓存、失败样本和人工标注平台都可能形成数据副本。

解析阶段应忠实保留内容，但给可疑隐藏内容打标签；执行策略必须由下游模型网关控制。权限过滤要在召回前执行，不能指望模型“看到了但不回答”。

## 十八、什么时候用规则，什么时候用模型

推荐遵循以下顺序：

1. 文件格式原生结构最可信，优先使用；
2. 稳定版面使用确定性坐标和规则；
3. 复杂版面使用专用布局/表格模型；
4. 模糊图片、图表和非标准结构再使用视觉语言模型；
5. 低置信度结果进入人工复核。

大模型适合解释复杂语义，不适合替代所有确定性解析。它可能补全不存在的表格值，也可能每次输出不同结构。若使用模型参与解析，应保存模型名称、提示词版本、输入区域、原始输出和置信度，并用 Schema 严格验证。

## 十九、把整条流水线串起来

下面的伪代码刻意省略具体库细节，用来强调阶段边界：

```python
def process_document(upload):
    asset = ingest_and_scan(upload)
    identity = detect_file_type(asset)
    strategy = route_parser(identity, inspect_document(asset))

    raw_result = extract_content(asset, strategy)
    normalized = normalize_safely(raw_result)
    structured = rebuild_structure(normalized)
    cleaned = denoise_with_structure(structured)
    semantic_units = build_semantic_units(cleaned)
    chunks = chunk_by_structure(semantic_units)
    enriched = attach_metadata_and_acl(chunks, asset, strategy)

    report = validate_pipeline(asset, raw_result, structured, enriched)
    if report.has_blocking_error:
        return send_to_review(asset, enriched, report)

    persist_versioned_artifacts(asset, raw_result, structured, enriched, report)
    return enriched
```

真正的工程重点是每个函数都有明确输入输出，并且中间结果可保存、可比较、可重跑。不要把所有逻辑写进一个 `load_and_split()`。

## 二十、如何接入 LangChain 或 LlamaIndex

当输出已经是统一 Chunk 后，接入框架只是适配工作：

- `text` 作为页面内容；
- 标题路径、页码、sheet、单元格范围等进入 metadata；
- ACL 和租户字段进入向量库过滤字段；
- `chunk_id` 作为稳定主键；
- `document_version` 用于更新和删除旧索引。

不要依赖框架自带 loader 的默认结果来定义你的文档模型。框架可以替换，解析资产和质量标准应该长期稳定。

## 二十一、上线前检查清单

### 文件接入

- [ ] 不只依赖扩展名判断格式
- [ ] 有大小、页数、解压比、超时和内存限制
- [ ] 原件只读保存，计算稳定哈希
- [ ] 密码、损坏、旧格式和恶意文件有单独状态

### PDF

- [ ] 能区分数字、扫描、混合和损坏文本层
- [ ] 保留文字块坐标、页码和阅读顺序证据
- [ ] OCR 支持方向、倾斜、语言和置信度检查
- [ ] 多栏、跨页表格、脚注、图片和公式有策略

### Word

- [ ] 段落和表格按原始顺序遍历
- [ ] 标题、编号、列表和 section 得到处理
- [ ] 文本框、修订、脚注、图片等不会静默丢失
- [ ] `.doc` 和密码文件有回退流程

### Excel

- [ ] 一个 Sheet 可以识别多个表格区域
- [ ] 公式与缓存值分别保存
- [ ] 多级表头、合并单元格、单位得到保留
- [ ] 隐藏内容、外部链接和权限边界有明确规则
- [ ] 大表按业务主键或行组切分，而非每格一个块

### 去噪与切块

- [ ] 原文与清洗文本可对照
- [ ] 页眉页脚使用跨页证据识别
- [ ] 按 Token 和语义边界切分
- [ ] 表头、标题路径和来源不会与正文分离
- [ ] 每个 Chunk 都有稳定 ID、来源和 ACL

### 质量与运维

- [ ] 有黄金文档集和真实问题回归测试
- [ ] 有成功、警告、复核、隔离和失败分级
- [ ] 中间产物按版本保存，可局部重跑
- [ ] 指标能发现空页、乱码、错序和异常块
- [ ] 日志、缓存和第三方服务满足隐私要求

## 结语

RAG 文档解析不是“从文件中取出字符串”，而是把面向人类排版的文件，转换成机器可理解、可检索、可验证的知识单元。

一条可靠流水线应始终坚持四件事：

1. **先忠实提取，再谨慎清理；**
2. **先恢复结构，再进行切块；**
3. **任何自动判断都要留下证据和置信度；**
4. **任何检索结果都必须能回到原文件和原位置。**

当回答质量不好时，不要第一时间更换 Embedding 模型或向量数据库。先打开被召回的 Chunk，沿着页码、坐标和处理记录回到原文，检查内容是否在解析、去噪或切块阶段已经被破坏。能够完成这条反向链路，才算真正建立了可维护的 RAG 文档解析工程。
